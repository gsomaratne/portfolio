Kairos — Policy-as-Code

Client Capital One
Timeline Ongoing — 3 versions to date
Role Embedded product designer
Team Kairos tech team

Overview

Kairos is Capital One's enterprise policy-as-code platform: tenants author and deploy Rego policies, governance owners approve requirement changes, and downstream systems consume enforcement decisions. The team builds it with heavy use of Claude Code, which accelerated development past the point where design could keep pace by reviewing every screen.

Rather than wait for Capital One's Gravity design system to ship a machine-readable, agentic layer, I co-authored DESIGN.md with the Kairos tech team — a design markdown that lets a coding agent generate UI to real design standards today, with design judgment encoded as rules it can check itself against.

Problem

A dev team shipping UI faster than design could keep up with.

No single design system was enforced across the app, and it showed: corner radii, hover states, fonts, and even button and tag styles varied page to page. An engineer prompting an agent to "build the requirements table" isn't hand-rolling divs — they're delegating the UI decision entirely, and the agent has to decide on its own what a compliant button, badge, or modal looks like, with no designer in the room.

An audit of the Kairos repo showed what happens without any guardrail:

2,668 Raw Tailwind color classes used instead of design tokens
32 Files with hardcoded hex colors
36 Hallucinated components; 21 have a direct Gravity or Omni counterpart
111 Files touched by those components

"Hallucinated" is the precise word: each of those 36 components was the agent independently inventing a UI primitive that Gravity or Omni already shipped, because nothing told it otherwise. 28 were built on headless libraries like Radix, shadcn, and Recharts; 8 were built from scratch. Every one is visual debt, plus compute and context spent generating something redundant that later has to be found and fixed.

The reframe

I can't hand a developer my taste, and a manual migration of the whole app onto a design system was never going to be the roadmap. But I can hand an agent a document precise enough that it doesn't need taste to follow it — and that raises the floor of what ships, whether I'm in the loop on the prompt or only see the result afterward.

Approach

Why a design markdown, and why now.

A design markdown is a plain markdown file that gives AI coding agents structured design tokens and visual rules: a YAML front-matter block of machine-readable tokens (color, typography, shape, spacing, components), paired with a prose body that expands each one with rationale an agent can act on.

The better long-term answer is a mature agentic design system that serves this context on demand, and Gravity is expected to ship one — but it isn't ready yet. A markdown file is readable by people, parseable by machines, easy to version and diff in a pull request, and drops into a repo with no new tooling. That made it worth building as a stopgap rather than waiting.

It was meant to do three things: generate new UI in Gravity and Omni styling, audit existing UI for drift, and migrate existing UI onto the system. It took three versions to get the first one working.

1

v1, developer-led: right components, haphazard everything else. A developer installed Gravity tokens and Omni components and gave the agent a preference order: use them first, and fall back to Tailwind or local components only if neither covered the case. It generated the correct components and component-level styling (color, corner radius, border width), but spacing and text alignment were haphazard, producing a disjointed interface.

2

v2, designer and developer: better new UI, migration still fails. I worked with the tech team to add spacing and typography tokens and bring in Gravity's foundations — its standards for page layout, spacing, typography, color, and data visualization. New UI came out with the right components and much better styling. But pointed at an existing screen and asked to migrate it, the same document made inappropriate component and styling choices.

3

v3, orchestrator and topic docs (current). DESIGN.md became an orchestrating file that routes agents to docs/design-system/, with one file per foundation — colors, spacing, typography, elevation, corner radius, border, iconography, illustrations, animation, and data visualization — each holding tokens, do's and don'ts, and notes specific to this repo. An agent jumps straight to the rule it needs instead of parsing one long file. This version has a tech commitment for the next PI, and developers are testing it now.

Current state

Generation works. Migration doesn't yet.

Phase 1 · Complete

Generate new UI

Instructions for agents to adopt Gravity and Omni tokens, styles, and components in new UI. This is the phase that works.

Phase 2 · In progress

Templates and migration

Page-level templates (list, detail, dashboard) so agents start from a known layout, plus more precise instructions for migrating existing UI.

Phase 3 · Not started

Converge with Gravity

Build on Gravity's agentic design system once it ships. This work is meant to be superseded, not permanent.

A generated Rego rule builder — form fields, live code preview, condition rows — reads clean and on-brand, evidence the v1 to v2 progression worked for new screens. Gaps remain even there: alignment can slip, the agent defaults to cards for content groups even when a card isn't the right fit, and rules aren't always followed — hyperlinked text isn't always styled in the interactive color token.

Migration is the harder, unsolved half. Asked to bring the existing Requirements Registry onto Gravity, the agent produced haphazard margins and layout, rendered contextual menus and modals with transparent backgrounds instead of solid fills, and missed hidden interactions like drawers and expandable rows entirely — because nothing in the document told it those patterns existed on the page.

Two alternatives are complementary rather than competing, and worth revisiting once Phase 2 succeeds or stalls:

Build-time lint rules

Block hardcoded hex, arbitrary Tailwind values, and raw HTML in favor of Gravity and Omni. Enforces the standard whether or not the doc is read and catches drift before merge — but it's real engineering work to tune, risks false positives, and only prevents new violations, not the ~2,500 already in the app.

A dedicated migration initiative

Migrate existing screens on a known timeline for a clean baseline — but it costs tech-team bandwidth, competes with feature work, needs product prioritization, and if agent-led, inherits the same reliability problem this effort hasn't solved yet.

Open questions

What's still unresolved.

  • The illustrations doc has agents generate placeholder SVGs for a person to swap with real Gravity illustrations. Is there a better way to point agents at illustration files directly — a folder convention, or a change-management process?
  • How can the document format itself be optimized, independent of what's in it?
  • Does the agent complete the same task the same way every time? That hasn't been measured yet, and until it is, any claim of reliability is aspirational.
  • How should this hand off to Gravity's own agentic system once Phase 3 is possible?

Takeaways

A stopgap, on purpose.

Only generating new UI works so far. Auditing existing UI for drift and migrating it onto Gravity are both still open, and I'd rather say that plainly than round it up.

This isn't the end state either way. A truly agentic design system would expose component contracts, accessibility rules, and usage guidance as structured, queryable data — not prose an agent has to parse and hope it interpreted correctly. Every rule in DESIGN.md is something Gravity's platform could eventually serve on demand. Writing it by hand is what's possible now.

It's still worth doing. I can't be in every prompt, and I can't teach every developer taste in one sitting. But I can write down enough of that taste, as explicit, checkable rules, that the floor for AI-generated UI is meaningfully higher.

My role, specifically:

  • The v2 collaboration — introducing spacing and typography tokens and Gravity's foundations, which is what made new-UI generation reliable.
  • The v3 restructure — co-designing the orchestrator-plus-topic-docs split with the tech team once one flat file couldn't hold generation, audit, and migration guidance at once.
  • Encoding design judgment as rules — when a hallucinated component is really a Gravity primitive in disguise, why a card isn't always the right container, and why hidden interactions like drawers have to be named explicitly.
  • Not in scope — the Gravity and Omni component libraries themselves, or a manual migration of the app.
